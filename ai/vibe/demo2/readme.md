# Vibe coding Harness 工具

## Git
- Head 指针
指向当前所在的分支， 所在的版本。
git reset --hard  丢弃目前的修改  直奔那个版本，仓库时干净的 重新写Prompt
git reset --soft  不会丢弃工作区的修改会去到那个版本进入暂存区之后。 生成的局部修改 text title
回退到历史的任意版本

git restore --staged readme.md 将暂存区的代码移除，工作区
git checkout -- readme.md 丢掉工作区的修改


## Vibe Coding 开发前的步骤和关键点
通过vibe coding 项目推进特别快，但是越往后，代码越乱，慢慢变成屎山。越改越差，最后整个项目崩盘。

问题在哪？不在于AI 是强还是不强。

问题在于Vibe coding 他不是说把这个活直接丢给ai就可以去喝咖啡了。
而是你还要构建一套工程流程，去驾驭AI 。 Harness Engineering
前端工程化是 Vite 。

## Vibe Coding 标准工作流
规划就是一切
### 开发前9个步骤
- 第一个阶段叫定图纸
1. 先别去写代码，先去到需求。就好像你去跟朋友聊天一样，可以和claude 聊天 ，把痛点（足够痛 没解决，有市场），把目标用户，把使用场景和你理想中的核心功能
全部讲给AI，不用追求严谨，信息量，定完需求 
2. 定完这个需求后，把这个需求整理成一个PRD文档，你来验收。让AI输出一份比价结构化的文档，他中间包括了功能列表，用户流程，页面清单，每个功能你都要补上一句，到底做到什么程度才算完成（边界）？
比如： 登录成功，不是一句话，要说清楚 登录失败提示什么，登录成功以后跳转到哪里？ （首页，登录前的页面？）
没有验收标准，ai写的越来越发散。
PRD.md
3. 提前订好视觉，和页面框架
找2-3个参考网站，或者让Ai去生成几种风格的方案. 我们决定，网页的布局，页面有哪些内容，整体使用简约风格还是豪华风？
未来后面，不让ai 一边去写功能（逻辑），一边去把ui 推倒重来
- 第二个阶段打地基
4. 明确项目的边界和非功能需求，本地跑？ 还是线上公开的？ 用户量多少？ 有没有用户数据，支付，
性能和成本有没有上限？
安全，性能，可用性，成本 这四个非功能性需求不写清楚，后面一定会返工。
- 锁定技术栈，越可验证越好。
适合的就是最好的，React + TS + Tailwindcss 
claude.md

- 第二个阶段 让ai出轻量架构草案
目录架构这么分层
核心模块有哪些
数据模型长什么样
有哪些组件
- 第三阶段 立规矩
7. 固化成文档
现在的Agent 和llm 交互都会用一个文档，需要把prd 设计 架构 当前状态
写成项目根目录下的几个文本，固化下来
PRD.md(产品需求文档)
project.md(项目需求文档)
....
design.md(设计文档)
都是ai的全局上下文， vibe coding 永久约束
8. 定开发规范和建参考文档或资料
- 错误处理
api 接口
restful 规范
可以给以个样本参考
9. 搞好git 和质量阀门
